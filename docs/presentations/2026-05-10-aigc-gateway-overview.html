AIGC Gateway 第二幕 · 核心理念
主线 · 之一

Action — Prompt 一等公民

一个 Action = 一个模型 + 一个参数化模板 + 一份变量定义。
像数据库表、像 API endpoint，可命名、可版本、可观测。

参数化
{{variable}} 占位，调用时校验、渲染、注入
版本固定
v1 / v2 / v3 共存，activate_version 一键切活跃版本，回滚不用发版
Dry-run 预览
免费渲染变量、检查模板，不真正调模型
跨业务复用
业务代码不嵌 prompt，前端/后端/脚本通过 ID 引用同一个 Action
// 业务代码现在是这个样子
await gateway.runAction('summarize-doc', {
  doc: longText,
  style: 'bullet',
})

// 不是这个样子
const prompt = `你是一个文档摘要助手...
请把以下内容总结为 3 个 bullet：
${longText}
风格要求：${style}...
（200 行 prompt 写死在这里）`
await openai.chat.completions.create({...})
AIGC Gateway 第二幕 · 核心理念
主线 · 之二

Template — 多步编排

把多个 Action 按顺序或并行组合成工作流。业务代码不再做"先调 A，拿结果再调 B"的胶水。

Sequential（串行）
每步自动注入 {{previous_output}}
Step 1→ Step 2→ Step 3
典型场景：原始素材 → 提取要点 → 生成正文
Fan-out（并行分拆）
SPLITTER → BRANCH × N → MERGE
SPLITTER→ ·×N→ MERGE
典型场景：长文切段 → 并行翻译/打分 → 汇总结果
Template 是 可执行的 prompt 工作流，业务侧只关心输入和输出，中间的多步链路被治理在网关内。

AIGC Gateway 第三幕 · 研发过程
1 个人 6 周交付的秘密

Triad Workflow — 不是更努力，是更结构化

Planner
需求拆解 + 规格
读 backlog、写 spec、拆 features.json、做架构决策、维护记忆
Generator
按规格写代码
不发明需求、不评估自己 — 只把 spec 翻译成可运行的代码
Evaluator
设计测试 + 签收
独立工具，避免"自己评自己"，输出 signoff 报告或反馈打回 fixing
状态机
new→ planning→ building→ verifying⇄ fixing⇄ reverifying→ done
每个批次都走完整闭环。没走完不能进下一批。
AIGC Gateway 第三幕 · 研发过程
把"工程纪律"变成"协议"

规格驱动闭环 + 分层记忆

规格驱动

  • spec.md — Planner 写、Generator 读
  • features.json — 每条功能可独立追踪
  • progress.json — 当前阶段 + 角色分配
  • signoff 报告 — Evaluator 给出 PASS/FAIL
过程产物本身 = 可审计的工程证据

分层记忆（T0 / T1 / T2）

  • T0 必读 — 项目状态、环境信息（每次启动）
  • T1 角色 — 当前角色的行为规范
  • T2 按需 — 触发条件命中才加载
上下文窗口是稀缺资源，分层加载就是节流

AIGC Gateway 第四幕 · 经验教训
最终 takeaway · 可外溢到任何项目

三条可复用经验

01
Prompt 工程化的边界
值得做：业务方反复调文案 / 多处复用同一段逻辑 / 需要 A/B 不同版本 / 生产环境
不值得做：一次性脚本 / 单条简单调用 / Demo 阶段 — 别为了优雅过度抽象
02
AI 协作开发的核心，不是 prompt，是状态机 + 记忆分层
协作不是"我和 AI 一起写代码"，是"我设计流程，AI 走流程"。
没有状态机 → 失忆 / 重复劳动 / 无法接力；没有记忆分层 → 上下文爆炸 / 注意力稀释。
03
过程产物 = 产品的一部分
spec / features.json / signoff 报告 不是"开发废纸"，是工程纪律的载体。
纪律可以外溢 — harness-template 已独立成 repo，下一个项目直接复用。
